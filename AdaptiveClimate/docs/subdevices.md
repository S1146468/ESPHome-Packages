# Stijn learner as an ESPHome sub-device

This is entity grouping only, based on reviewed commit
`c9b98da68d882c1f12a2bafd5714ce67ed4a7096`. All Python/C++ component files and the
numerical tests remain unchanged. The learning interval, freshness default,
24-accepted-sample warm-up, forecast horizons and all safety guards are retained.

## Minimal change to your existing thermostaat.yaml

Keep your existing `esphome.name`, friendly name, API integration, areas, inputs,
PID packages and boiler configuration. Append this one entry to `esphome.devices`:

```yaml
    - id: adaptive_climate_stijn
      name: Adaptive Climate Stijn
      area_id: kamer_stijn
```

Do not replace the existing `climate_stijn` or `climate_nick` entries. Reuse the
already declared `kamer_stijn` area (display name `Kamer Stijn`); do not declare it
again. The new device definition belongs under `esphome`, not `adaptive_climate`.

In the existing named `packages.stijn_observer.files` entry, add only:

```yaml
        vars:
          device:
            id: adaptive_climate_stijn
            name: Adaptive Climate Stijn
```

Merge those keys into the existing `vars` mapping, preserving:

```yaml
          observer_id: stijn_thermal_model
          observer_name: Stijn
          room_temperature_id: climate_stijn_temperature
          outdoor_temperature_id: outside_temperature_sensor
          valve_command_id: climate_stijn_valve_opening_degree
          supply_temperature_id: ch_temperature
          heating_active_id: boiler_active
          window_open_id: climate_stijn_window
          dhw_active_id: dhw_active
          observer_stale_after: 15min
```

Point the existing package and external-component source refs at
`feature/adaptive-climate-subdevices` (or the same reviewed commit). Keep their
named-package/external-component structure and paths. Do not load the old and
new observer packages together. The [complete merge snippet](../examples/stijn_integration.yaml)
contains only these additions and preserved mappings, with no sensor definitions
or new physical node. It is not a replacement for your complete device YAML.

## Exactly seven learner entities

Every output, including status, uses native `device_id: ${device.id}`:

| Name (unchanged) | YAML ID (explicit, internal to ESPHome) | Unit / precision |
| --- | --- | --- |
| Stijn Forecast 15min | stijn_thermal_model_prediction_15min | °C / 3 decimals |
| Stijn Forecast 30min | stijn_thermal_model_prediction_30min | °C / 3 decimals |
| Stijn Forecast 60min | stijn_thermal_model_prediction_60min | °C / 3 decimals |
| Stijn Model Residual RMSE | stijn_thermal_model_residual_rmse | °C / 3 decimals |
| Stijn Model Training Samples | stijn_thermal_model_training_samples | Count, no unit / integer |
| Stijn Model Heating Excitation | stijn_thermal_model_heating_excitation | Dimensionless, no unit / 3 decimals |
| Stijn Model Status | stijn_thermal_model_status | Text |

All are diagnostic entities with explicit icons. Forecasts have temperature
device class. RMSE is an error magnitude, so it is not given absolute-temperature
device class. Training samples and excitation are neither temperatures nor
percentages. Names deliberately keep the existing `Stijn` prefix; using only
`Forecast 15min` would introduce an unnecessary identity change.

The package consumes `device.id`, matching ClimateDevice/ClimateDebugSensors.
`device.name` is accepted for that convention, but the main `esphome.devices`
definition supplies the device's actual name. `observer_name` still supplies
entity labels. No devices or input sensors are created by ObserveRoom.yaml.

## Identity and Home Assistant migration

These identifiers are different:

- ESPHome YAML `id`: an internal code-generation reference. The model ID stays
  `stijn_thermal_model`; explicit output IDs replace previous autogenerated IDs.
- API entity key/object name: derived from the unchanged entity name in ESPHome
  2026.10.0. Adding an explicit YAML ID does not itself change that name/key.
- Home Assistant integration unique ID: includes the sub-device namespace.
  Moving from device 0 to a named sub-device necessarily changes this identifier.
- HA `sensor.*` entity ID: a registry-managed name that can be retained when HA
  migrates the unique ID and device assignment.

It is not possible to guarantee an unchanged device-aware unique ID while using
native sub-device grouping. No custom unique-ID override or C++ workaround is
introduced. [HA 2026.10.0's ESPHome entity code](https://github.com/home-assistant/core/blob/2026.10.0/homeassistant/components/esphome/entity.py)
handles named entities moving between devices by updating the registry and
re-adding the entity to the correct device. Keeping all seven names unchanged
supports that migration. The installed HA version and current registry state
still determine the outcome; this has not been tested against your live HA instance.

## Verify before cleaning anything up

1. Before an authorised firmware update, make a Home Assistant backup including
   its database. Record the seven current `sensor.*` IDs, entity names, custom
   names and dashboard/automation references. Save your working firmware/config.
2. Keep HA running during the firmware reconnect so it can recognize the previous
   named entities. After reconnect, open Settings → Devices & services → ESPHome
   and inspect the existing integration. Expect the original three devices plus
   `Adaptive Climate Stijn`, with exactly seven learner entities in `Kamer Stijn`.
3. Check all seven old `sensor.*` IDs still resolve, receive updates, and show their
   earlier History. Check the status text sensor too. The original room inputs,
   PID controls and boiler entities must still be on their original devices.
4. If the device area is not assigned as expected, check its HA device settings and
   select the existing `Kamer Stijn` area. HA's existing user area assignment may
   take precedence over firmware-provided placement.
5. If placement looks stale, reload this existing ESPHome integration once and
   inspect its logs. Do not delete/re-add the integration or delete any original
   thermostat/PID device as a troubleshooting shortcut.
6. If duplicates such as `_2` appear, first identify which entity receives live
   updates and which is unavailable. Compare their ESPHome integration, device,
   names and recorded IDs. Disable the unavailable duplicate as a reversible first
   step; do not purge Recorder data or edit `.storage` files.
7. If automatic migration cannot be recovered and you choose manual registry
   cleanup after backup, rename only the confirmed unavailable learner entry's
   entity ID to an unused `_legacy` ID, then rename the confirmed live learner
   entry to the original recorded `sensor.*` ID. Verify History, statistics and
   references before removing any disabled orphan. Renaming can affect history
   presentation/statistics and is not a guaranteed history merge; restore the
   backup or retain the disabled orphan if continuity cannot be verified. Leave
   the original three devices and all their control entities alone.

No cleanup is needed when automatic migration succeeds. Hardware/HA verification
is a later user-run step; build tests cannot establish the live device-registry
result. Reboot still resets the observer's unpersisted model, as before.

## Later: Nick (not enabled by this change)

For a future Nick observer, append a different device ID such as
`adaptive_climate_nick`, name `Adaptive Climate Nick`, area `kamer_nick`, and use
that ID in a separate observer include. Choose a unique observer ID and Nick's
existing sensor mappings. Do not add that include now. The generic two-room
example is only a reusable build example, not an enabled Nick observer in your
Stijn integration.

## Evidence and conventions

- Existing `Thermostat/ClimatePID/ClimateDevice.yaml` and `ClimateDebugSensors.yaml`
  put `device_id: ${device.id}` on their exposed entities; that mechanism is reused.
- ESPHome 2026.10.0 `config_validation.ENTITY_BASE_SCHEMA` accepts device references;
  `core.entity_helpers._setup_entity_impl` emits `set_device_` for both numeric and
  text sensors through their normal registration functions.
- [ESPHome devices and areas documentation](https://esphome.io/components/esphome/#devices)
  describes logical devices within one node. Tests inspect expanded YAML and
  generated C++ assignments, including the model-status entity.
