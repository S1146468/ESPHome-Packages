## Rollback gate and controlled deployment plan

**There is currently no verified current-device rollback image. Do not install
until that gate is closed.** A freshly rebuilt old YAML is not an exact backup.

Before any approved installation:

1. Back up the actual HA ESPHome YAML, secrets privately, complete `.esphome`
   directory, cached repositories with Git refs/reflogs, build log, generated
   source, ELF, OTA binary, factory image, partition table and `flash_args`.
   Preserve timestamps and SHA-256; do not overwrite the only known-working files.
2. Recover the last successful installation record if available, then associate
   its exact application/ELF digest with device identity and current build
   information. A compile log alone establishes a build, not installation.
3. If that association cannot be recovered, arrange a separately approved
   maintenance window to back up the actual flash before updating. Serial ROM
   access normally resets/stops the ESP32 and interrupts thermostat operation;
   **no such read or reset was performed here**. Confirm flash size, partition
   layout, active OTA slot, secure-boot/encryption status and the safe heating
   fallback first. Do not assume the candidate's 4 MB layout is the running one.
4. Read the full flash twice without writes and compare cryptographic hashes.
   Keep the device-bound dumps private: they may contain Wi-Fi/API credentials,
   NVS and OTA metadata. Extract the active app using the actual partition table
   and OTA selection, not a guessed app offset. Check its ESP image checksum/hash
   with `esptool image-info`, record the embedded application ELF digest, and
   retain the verified OTA app plus full-flash recovery image. The backup manifest
   must identify the actual device and the method/date of acquisition.
5. Verify the recovery route: correct USB/serial interface and boot access, tools,
   documented offsets from the saved layout, authentication for OTA, and operator
   access if Wi-Fi/API fails. A hash check verifies file consistency; an actual
   recovery rehearsal needs a spare equivalent device or an explicitly approved
   maintenance test. Until then label recovery **prepared, not demonstrated**.
6. Build the candidate with the real existing secrets privately, preserving the
   pinned revisions, and record final code/toolchain/image hashes. Re-run the
   comparison and tests. The public dummy-credential images built here are
   evidence only and must not be installed.

After **separate approval**, use a supervised application-only OTA installation
with stable power and a safe manual heating fallback. Keep the known-running
image and partitions untouched in the recovery archive. Restarting resets PID
integral/runtime state and both in-RAM learners, even though their code is
unchanged; keep this commissioning period out of accuracy comparisons.

If heating behavior, API connectivity, watchdogs, memory or timing fail, stop the
experiment and use the saved exact application through the known OTA recovery
route. If OTA is inaccessible, use the verified serial/full-flash procedure for
that device/layout in the maintenance window; preserve NVS and do not erase all
flash or substitute an unrelated factory image. Verify post-restore identity,
configuration, connectivity, CH/DHW flags, valve commands and target-water behavior.
Record the rollback result and exclude the interrupted validation block.

The candidate build enables ESP-IDF application rollback, but the running
bootloader/OTA state is unknown and a bootable app with incorrect heating logic
may still be marked valid. Automatic boot rollback is **not** the control-behavior
recovery plan. See [ESP-IDF OTA behavior](https://docs.espressif.com/projects/esp-idf/en/v5.5.6/esp32/api-reference/system/ota.html)
and [esptool image/read/write command documentation](https://docs.espressif.com/projects/esptool/en/latest/esp32/esptool/basic-commands.html).

## Runtime records and limitations

The two new records publish once per scheduled five-minute cycle, including
suspension; no new high-frequency entity or flash write is added. Either record
is individually optional. Omit `runtime_record` and its probe-source keys to
disable timing/heap/stack collection; omit `input_record` to disable snapshots.
Neither learner header is edited by this step.

```
i1|boot|q|t|room,outdoor,valve,supply|room_age,outdoor_age,valve_age,supply_age|states|flags|api
r1|boot|q|t|free,min,largest,stack|original_us,shadow_feed_us,shadow_forecast_us,update_us|cycle_dt,jitter|loop_gap,pid_gap,writer_gap|pid_late,writer_late
```

`boot` is a shared per-process random tag (not persisted/device identity), `q/t`
match the existing cycle, and ages are integer **milliseconds since raw callback**.
`null` means unseen/nonfinite. States, in room/outdoor/valve/supply order:
0=missing, 1=invalid, 2=health unavailable, 3=strict expired, 4=recent receipt,
5=event-held. Flags are CH/window/DHW (`0`, `1`, or `?` unknown); `api` says the
configured API-connection policy passes. The current YAML has no separate
physical sensor health binding, so receipt/HA validity is not physical freshness.

Heap quantities use internal 8-bit-capable RAM in bytes. `min` is the ESP-IDF
minimum free heap since boot, `largest` the largest free block at sampling,
`stack` the current loop-task minimum free stack since task creation, in **bytes
on ESP-IDF**, not words. Other tasks' stacks are not measured.

Work maxima are microseconds since boot: original observe + actually requested
original rollouts; one complete shadow input handler (including actual publication
learning); three requested shadow rollouts; and whole completed observation
callbacks including publication/instrumentation. The currently publishing whole
callback finishes after its record, so its total first appears in the next
record. These are measured maxima, not proven hard real-time WCET bounds.
Zero timing/gap fields can mean no relevant callback has occurred yet or a probe
was not configured; they are not evidence of zero cost or perfect scheduling.

Cycle delta/jitter and loop/PID-input/water-target maximum gaps are milliseconds.
Jitter is absolute deviation from 300,000 ms. The PID probe watches existing
filtered room-heartbeat callbacks; it does not refresh raw timestamps or supply
training samples. The writer probe watches the existing target-water sensor's
raw callbacks, not valve or OpenTherm outputs. `late` counts observed gaps >5,250
ms against their existing 5-second cadence. Main-loop gaps and these proxies
can detect stalls but cannot establish exact PID execution, writer-action or
OpenTherm request/response latency, nor attribute causality to learning. Existing
sync OpenTherm, Wi-Fi/API, Recorder and other work can contribute. No new OpenTherm
hook, control callback replacement or output interface was introduced.

## Recorder-first collection and installation checklist

[Home Assistant Recorder](https://www.home-assistant.io/integrations/recorder/)
already stores state history by default. If there are no exclusions, no new
collector or include allowlist is required. Merge `recorder_shadow_example.yaml`
into the **one existing** Recorder block only as needed; do not replace existing
history policies or exclude unrelated home entities. Use registry-verified exact
IDs if renames mean the provided globs do not match. Explicit include entities
take precedence; explicit entity exclusions can defeat glob includes. Set enough
retention (35 days proposed), check database disk headroom, retain backups before
purging, and preserve raw states and climate attributes rather than long-term
statistics alone. No Home Assistant configuration has been applied by this task.

Recorder captures changes, not a guaranteed stream of identical physical sensor
readings. A `last_reported` update is distinct from a state-change/history event;
do not manufacture physical freshness from a repeated cached value. The changing
`q/t` ensures every received atomic observer record has a distinct state. See
[HA publication semantics](https://contributors.home-assistant.io/blog/2024/03/20/state_reported_timestamp/).

Before installation:

- [ ] Confirm the supplied YAML is the current intended configuration and preserve
      its pinned packages, secrets and complete build/cache backup.
- [ ] Establish current-device image identity or acquire/verify its backup as
      described above; resolve partition/encryption and recovery access.
- [ ] Review exact source diff, learner seals, control comparison, full test suite
      and complete ESP32/ESP-IDF build evidence. No dummy image may be installed.
- [ ] Freeze the approved checkout/manifest and build privately with real existing
      secrets; retain candidate and rollback hashes separately.
- [ ] Prepare Recorder retention/filter changes, entity mapping, backups and safe
      heating fallback; arrange supervised access and explicit approval.
- [ ] **STOP until the user explicitly approves installation.**

Only after approved installation:

- [ ] Verify unchanged PID/OpenTherm configuration and normal existing heating,
      CH/DHW/window/supply/valve behavior without autotuning or changing targets
      for this experiment.
- [ ] Enable any HA-disabled diagnostic entities; confirm both rooms have matching
      boot/q/t records and valid null/unavailable handling. Match original numeric
      forecasts to their cycle arrays; record shadow withholding honestly.
- [ ] In HA History, confirm both raw room sensors, every atomic text record,
      runtime record, state/age record, climate attributes and operation signals
      are actually retained. Check one backup/export preserves raw JSON/pipe
      strings and timestamps, not only plotted/downsampled values.
- [ ] Observe commissioning resource/cadence budgets; inspect anomalies before
      collecting a ranking period. Keep a supervised rollback option available.
- [ ] Freeze and record the independent validation start/end, then apply
      `VALIDATION_PROTOCOL.md` unchanged. Python collectors remain optional.

For export, prefer a Recorder database backup or full-resolution history with
entity IDs, state, last-changed/updated timestamps and climate attributes. Verify
it includes full atomic records and explicit unavailable states. UI graphs and
long-term aggregated statistics are insufficient. The existing external Python
collector is only an optional supplement for tighter receipt/liveness evidence;
no process needs to run outside ESP32 + Home Assistant for initial collection.
